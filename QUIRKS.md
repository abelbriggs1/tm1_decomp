# QUIRKS.md

This is a file for compiler quirks and other issues that may prevent
code and data from matching.

(Much of this will be uploaded to `decomp.wiki` in the future if it's determined
to be applicable to other games.)

## Small data must be decompiled early

The toolchain that we use for this repo treats the following variables
differently when attempting to load/store to them.

```
extern s16 my_var;
static s16 my_var2;
```

Data in small-data sections (`.sdata`, `.sbss`) must be decompiled
into C variables before any C code that accesses them can be matched;
`extern` cannot be used for them.


## Inlining results in a variable reload

If you have two functions which use the same variable:

```c
uaSelectOpponents(gVehicleID, gCurrentLevel, &gNumOpponents, opponents);
screenInitCardSprites(gCurrentLevel, gNumOpponents, opponents);
```

By default, PsyQ will load `opponents` into a local variable, and keep it across
the two calls.

However, if these calls are placed as part of an inline function:

```c
inline void shellSelectCards(void)
{
    uaSelectOpponents(gVehicleID, gCurrentLevel, &gNumOpponents, opponents);
    screenInitCardSprites(gCurrentLevel, gNumOpponents, opponents);
}

void shellBeginLevelTransition(void)
{
    // ...
    shellSelectCards(); // inlined
    // ...
}
```

When inlined, PsyQ will treat each call as if it were in a separate context.
In this case, `opponents` will be reloaded across the two calls.

## Inlined struct/array operations

Many cross-member struct and array operations will be converted to
function calls. As detailed [above](#inlining-results-in-a-variable-reload),
these often can't be matched by using the raw/substituted equivalent explicitly
because they typically result in abnormal variable behavior (such as reloads).

### `memcpy()` (constant struct assignment)

Struct assignments such as the following:

```c
// all are `MATRIX`
cs->mat = unitMatrix;
cs->wmat = unitMatrix;
```

PsyQ accepts this syntax, and converts this to a call to the BIOS (not the SDK!)'s
`memcpy()`:

```c
memcpy(&cs->mat, &unitMatrix, sizeof(MATRIX));
memcpy(&cs->wmat, &unitMatrix, sizeof(MATRIX));
```

### `memset()` (partial struct/array assignment)

`memset()` behavior varies greatly depending on how the assignment is performed.
Similarly to `memcpy()`, the inlined calls here go to the BIOS `memcpy()`, not the SDK's.
Here is a table showing the general behavior:

| Source                                                     | Generated code |
|------------------------------------------------------------|----------------|
| `char buf[30] = "";`                                       | Copies the string literal (`lbu`/`sb`), then calls `memset(buf + 1, 0, 29)` |
| `char buf[30] = "ab";`                                     | Copies 3 bytes, then calls `memset(buf + 3, 0, 27)` |
| `int a[20] = {v};` (any non-constant element)              | Calls `memset(a, 0, 80)` on the whole array, then stores the elements |
| `int a[20] = {0};`, `{1}`, `Big b = {{0}};` (all constant) | No `memset`; a copy loop from `.rodata` |

## Inlined `memcpy()` (`-fbuiltin`)

Note that the `memcpy()` call generated by struct assignment is **always**
a function call; the copy is never inlined.

Some TUs do have inlined `memcpy()` calls on `structs` that are _not_ assignments.
If you know the `struct` layout, you can easily spot these by looking at the stride
of the copy operation in the ASM. If the stride is uniform and ignores the layout
of the `struct`, it's an inlined `memcpy()` call. For example:

```
	addu	$2,$23,$19
	sll	$2,$2,2
	lw	$3,gCharacterTemplate($2)
	lw	$4,gCharacterTemplate+4($2)
	lw	$5,gCharacterTemplate+8($2)
	lw	$6,gCharacterTemplate+12($2)
	sw	$3,0($17)
	sw	$4,4($17)
	sw	$5,8($17)
	sw	$6,12($17)
	lw	$3,gCharacterTemplate+16($2)
	sw	$3,16($17)
```

`gCharacterTemplate` is a `SPRT`, which has a non-uniform layout, but this is clearly
copying 4 bytes at a time.

If you encounter this behavior, a `__builtin_memcpy()` call will _technically_ match:

```c
__builtin_memcpy(sprite, &gCharacterTemplate[font], sizeof(SPRT));
```

**However, it is extremely unlikely that the developers invoked a builtin directly.**
Assuming the behavior is uniform across the file,
**it is incredibly likely that the developers compiled the TU with `-fbuiltin` instead.**
This enables PsyQ to optimize some calls by replacing them with inlined
`__builtin` equivalents.

## `do { } while (0)` affects codegen

`do while (0)` is a common method that developers used to create multi-line
macros. Using `do while (0)` allows the caller to add `;` on the end, making
the macro feel more like a proper function call syntactically. Additionally,
the macro has its own scope, so it can freely declare private variables.

Since `while (0)` ensures the block never loops, these two macros are
_semantically_ equivalent:

```c
/* Version A */
#define GET_SIZE(font, i, w, h)            \
    {                                      \
        *(w) = gGlyphs[(font)][(i)].width;  \
        *(h) = gGlyphs[(font)][(i)].height; \
    }

/* Version B */
#define GET_SIZE(font, i, w, h)            \
    do {                                   \
        *(w) = gGlyphs[(font)][(i)].width;  \
        *(h) = gGlyphs[(font)][(i)].height; \
    } while (0)
```

**However**, this can still change codegen because `do { } while (0)` technically
constitutes a loop.

### Register allocation / swaps

In more complex functions with branches, the use of `do { } while (0)` can change
register allocation. Given this example:

```c
typedef struct {
    u8 width;
    u8 height;
} Glyph;

extern Glyph* gGlyphs[];
extern int lookup(int c);

void getSize(int font, int c, u32* w, u32* h)
{
    if (c == ' ') {
        *w = 4;
    } else {
        int i = lookup(c);
        GET_SIZE(font, i, w, h);
    }
}
```

```

 subu  $sp,$sp,32             subu  $sp,$sp,32
 sw    $16,16($sp)        <   sw    $17,20($sp)
 move  $16,$4             <   move  $17,$4            # font
 move  $4,$5                  move  $4,$5
 sw    $17,20($sp)        <   sw    $16,16($sp)
 move  $17,$6             <   move  $16,$6            # w
 sw    $18,24($sp)            sw    $18,24($sp)
 move  $18,$7                 move  $18,$7            # h
 li    $2,0x20                li    $2,0x20
 bne   $4,$2,$L2              bne   $4,$2,$L2
 sw    $31,28($sp)            sw    $31,28($sp)
 li    $2,0x4                 li    $2,0x4
 sw    $2,0($17)          <   sw    $2,0($16)         # *w = 4
 j     $L3                    j     $L3
$L2:                         $L2:
 jal   lookup                 jal   lookup
 la    $3,gGlyphs             la    $3,gGlyphs
 sll   $4,$16,2           <   sll   $4,$17,2          # font * 4
 addu  $4,$4,$3               addu  $4,$4,$3
 lw    $3,0($4)               lw    $3,0($4)
 sll   $2,$2,1                sll   $2,$2,1
 addu  $3,$2,$3               addu  $3,$2,$3
 lbu   $3,0($3)               lbu   $3,0($3)
 andi  $3,$3,0xff             andi  $3,$3,0xff
 sw    $3,0($17)          <   sw    $3,0($16)         # *w = width
 lw    $3,0($4)               lw    $3,0($4)
 addu  $2,$2,$3               addu  $2,$2,$3
 lbu   $2,1($2)               lbu   $2,1($2)
 andi  $2,$2,0xff             andi  $2,$2,0xff

$L3:                         $L3:
 ...epilogue identical...     ...epilogue identical...
```

We can see that the register allocation changed; two registers were
swapped around.

(Note that this example replaces `do while(0)` with a plain `{ }` block.
While `{ }` blocks can also change codegen in some edge cases, in this example,
the output is identical whether or not the block is removed entirely.)

### Barriers

The use of `do { } while (0)` can also lead to a "barrier" effect which prevents
the compiler from reordering/optimizing memory accesses. For example:

```c
extern int gA, gB;
extern int gX, gY;

#define BARRIER do { } while (0)

void copy2(void)
{
    gX = gA;
    BARRIER; /* only in the barrier version */
    gY = gB;
}
```

```
 No barrier  With barrier
 lw $2,gA    lw $2,gA
 lw #3,gB    #nop
 sw #2,gX    sw $2,gX
 sw #3,gY    lw $2,gB
             #nop
             sw $2,gY
```

We can see that the barrier prevents the compiler from optimizing the delay slots of the
two `lw` instructions.

The "barrier" namesake is a bit clearer if we add more variables.

```c
extern int gA, gB, gC, gD;
extern int gX, gY, gZ, gW;

#define BARRIER do { } while (0)

void copy2(void)
{
    gX = gA;
    gY = gB;
    BARRIER;
    gZ = gC;
    gW = gD;
}
```

```
 No barrier	With barrier
 lw $2,gA	lw $2,gA
 lw $3,gB	lw $3,gB
 lw $4,gC	sw $2,gX
 lw $5,gD	sw $3,gY
 sw $2,gX	lw $2,gC
 sw $3,gY	lw $3,gD
 sw $4,gZ	sw $2,gZ
 sw $5,gW	sw $3,gW
```

When the barrier is absent, the loads are grouped together in order to efficiently
ready the stores. When the barrier is present, the loads and stores are split based
on which "side" of the function they're on.

**Note that barriers are a last resort for matching code. Use them sparingly.**
It is incredibly unlikely for the original developers to intentionally insert
empty loops into their code.
If struggling with register allocation or reordering, try to look for other possible
culprits, such as temp variables and pointer aliasing optimizations.

While developers didn't intentionally insert barriers, it is _possible_ that barriers
exist in the original compiled code. Most commonly, they can be an artifact of
stubbed debug macros whose contents were removed or disabled. Their presence is
more likely in TUs with a lot of `printf()` output and debug strings.
